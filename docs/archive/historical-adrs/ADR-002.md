# ADR-002: In-Process Python Isolation and GIL Redesign

## Context
The dynamic plugin architecture relies on loading Python scripts at runtime to define custom embedding models, LLM extractors, and tools. PyO3 is used to host the CPython interpreter in-process. 

However, in the previous implementation, FFI crossings utilized raw JSON strings, and blocking Python network operations (e.g. LLM HTTP requests via `urllib.request`) did not release the CPython Global Interpreter Lock (GIL). This locked the entire Python interpreter, causing concurrent background tasks (like consolidations or embedding generation) to stall.

## Decision
Retain in-process PyO3 native bindings to prevent the overhead and lifecycle complexity of out-of-process process supervision. Redesign the boundary to implement two strict rules:
1. Every call from Rust into Python must explicitly release the GIL (using `py.allow_threads`) when Python transitions to network or filesystem operations.
2. Redesign the FFI to map structured native PyO3 objects and dataclasses conforming to `brain_ai.api.v1` rather than serializing data to JSON strings twice.

## Consequences
- **GIL Contention:** Eliminated during network I/O; multi-threaded Rust workers can execute concurrent LLM requests without blocking.
- **FFI Overhead:** Reduced to microsecond levels by removing JSON serialization.
- **Portability:** Requires linking against a local CPython shared library at startup. This is mitigated by packaging support for Python 3.12/3.13 environments via `uv`.
