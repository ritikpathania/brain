# ADR-006: Retrieval Pipeline Extension Philosophy

## Context
With the implementation of the modular retrieval pipeline (PR-007), the retrieval architecture has been frozen. To prevent architectural drift and ensure a clear decision framework for future contributors, we need to document the extension philosophy for memory and retrieval components.

## Decision
Establish a strict two-path extension framework for all future retrieval and memory expansions:
1. **Adding a new data source/location**: Implement the `MemorySource` trait (e.g., `StmMemorySource`, `LtmMemorySource`, `EmbeddingMemorySource`, `GraphMemorySource`, `PluginMemorySource`, `RemoteMemorySource`).
2. **Adding a new ordering/ranking algorithm**: Implement the `RankingStrategy` trait (e.g., `Bm25Ranking`, `EmbeddingRanking`, `GraphRanking`, `RrfRanking`).
3. **Pipeline Orchestration is Frozen**: The `RetrievalPipeline` orchestrator itself (responsible for sequential execution, deduplication, early exit, timeout checks, cache hydration, and invoking ranking) must not be modified unless the fundamental orchestration semantics or overall control flow change.

This can be summarized in the following decision framework:

```
New retrieval locations
        ↓
Implement MemorySource

New ordering algorithms
        ↓
Implement RankingStrategy

Do not modify RetrievalPipeline
unless orchestration semantics change.
```

Furthermore, the data flow in the pipeline adheres to strict immutability disciplines:
* `RetrievalRequest` is immutable.
* `MemorySourceResult` is immutable.
* `SourceMetadata` is immutable.
* `PipelineAccumulator` is the only mutable working state wrapper inside the pipeline.

## Ranking and Scoring Invariants
To ensure stability, predictability, and safety across the retrieval architecture, all `RankingStrategy` implementations must adhere to the following invariants:
1. **Deterministic Tie-Breaking**: Whenever two nodes receive identical scores from a ranking algorithm, the tie must be broken deterministically: sort by `score DESC` first, then by `NodeId ASC` second.
2. **Embedding Dimension Independence**: Ranking code must never assume or hardcode vector dimensions (e.g. 384). If two embedding vectors differ in length, the similarity score must gracefully fallback to `0.0`.
3. **Decoupled Data Access**: Ranking strategies must remain pure scoring functions. They should not directly perform database operations or depend on broad repository interfaces; instead, they retrieve external parameters via focused traits (e.g., `EmbeddingLookup`).

## Future Evolution: RankingContext
As the retrieval orchestrator evolves, the signature of the `RankingStrategy::rank` method should transition from `rank(request, nodes)` to `rank(context)`, where `RankingContext` encapsulates:
- The immutable `RetrievalRequest`
- The list of candidate `Node`s to score
- Telemetry, telemetry tracing IDs, or diagnostic hooks
- Task cancellation signals/tokens
- Context-specific runtime configuration

## Consequences
- **Preventing Monolithic Growth**: Avoids turning `RetrievalServiceImpl` or `RetrievalPipeline` into a complex web of conditional logic. Each source and ranking strategy remains decoupled, isolated, and independently testable.
- **Maintainability**: Future developers have a clear, binary choice when introducing features: they either write a new `MemorySource` or a new `RankingStrategy`.
- **Architectural Integrity**: Preserves the simple, linear data flow from Request $\rightarrow$ MemorySource $\rightarrow$ MemorySourceResult $\rightarrow$ PipelineAccumulator $\rightarrow$ Ranking $\rightarrow$ Response.
