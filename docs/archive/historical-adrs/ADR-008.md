# ADR-008: Python Runtime and Plugin Extensibility

## Context
With the introduction of dynamic Python plugins and agents (PR-010), we need to establish clean architectural boundaries between the Rust host application and the embedded Python environment. To ensure robustness, parallel execution, and backward compatibility, we need to document key runtime stability invariants.

## Decision
Establish the following invariants for the Python runtime integration:

1. **Python Sandboxing via RuntimeContext**:
   - Python code is strictly sandboxed from direct access to host storage connection pools, session contexts, caches, and event dispatchers.
   - All interactions between Python and Rust must route exclusively through the `RuntimeContext` PyO3 class exposed under `brain_ai.api.v1` (or future version submodules).

2. **API Stability & Versioning**:
   - The Python API exposed to plugins is explicitly versioned (e.g., `brain_ai.api.v1`).
   - **Invariant:** New API versions may add capabilities, but they must **never** modify the behavior or signature of an existing API version. If breaking changes are required, a new submodule (such as `brain_ai.api.v2`) must be introduced, keeping the previous submodules completely unchanged.

3. **GIL Lifetime Discipline**:
   - The CPython Global Interpreter Lock (GIL) must be held only immediately before calling Python code.
   - Rust-side processing, database queries, and tool execution callbacks called from Python must be executed outside the GIL using PyO3's `py.allow_threads` wrapper.

4. **Dedicated API Models**:
   - To decouple Rust's internal domain types from public Python-facing APIs, the Python bindings wrap dedicated read-only API models (such as `MemoryNode`, `Conversation`, `ExecutionResult`) with getter methods and no setters, preventing dynamic plugins from mutating host-side state.

5. **Fault Isolation**:
   - The plugin loader operates with strict isolation. If a plugin fails during compilation, manifest parsing, or instantiation, the loader catches the exception, logs it, and continues loading other valid plugins. A single crashing plugin must never poison or fail the host runtime.

## Consequences
- **Decoupled API Lifecycles**: Future changes to Rust-internal storage models or services will not break third-party Python plugins, as the API models act as a stable DTO boundary.
- **Deadlock Prevention**: The disciplined release of the GIL prevents CPU threads from starving and eliminates deadlock risks during concurrent tool execution or retrieval.
- **Robust Startup**: Fault isolation ensures high availability, preventing incorrect scripts in the user's plugin directory from disabling the entire application.

## 6. Capability Evolution Policy
To ensure long-term stability and backward compatibility as extensibility capabilities grow:
- **Immutability of Existing Capabilities**: Existing capability semantics (e.g., Chat, Planner, Embedding, and Extraction) are immutable.
- **Graceful Forward Compatibility**: Unknown capability types defined in new plugin manifests must be gracefully ignored by older runtimes during parsing and loading, rather than causing loading failures.
- **ApiVersion Boundary**: Removing, modifying, or breaking the contract of any existing capability requires introducing a new `ApiVersion`.

## Future Evolution

### Generation-Based Runtime Contexts
If the runtime evolves to support asynchronous lifecycle hooks or callbacks that can outlive the original hook invocation, the boolean `is_valid` flag should be replaced with a generation/epoch token:
- **Structure**: `RuntimeContext` will hold a `plugin_id`, a `generation` token, and the host pointer.
- **Validation**: The `PluginManager` will increment a generation count whenever a plugin is unloaded or reloaded.
- **Verification**: Every host call will verify that the context's stored generation still matches the active registry instance generation, extending safety to async contexts.
