# RFC-002: Engineering Rules & Migration Plan

**Status:** FROZEN  
**Precedence:** Canonical Guideline  
**Change Policy:** Any changes to RFC-001 or RFC-002 require a formal RFC Amendment. Quiet architectural drift during implementation is prohibited.

---

## Part 1: Coding Standards & Engineering Rules

To prevent architectural drift and maintain structural integrity over years of modification, all commits must adhere to these 13 rules:

### 1. Dependency Graph Hygiene
No crate in the workspace may depend upward in the dependency graph. Circular crate dependencies are strictly forbidden. All upward communication must utilize event publishing or command dispatching.

### 2. Error Handling & Propagation
* Library crates (`brain-core`, `brain-storage`, `brain-python`, etc.) must exclusively use `thiserror` to define typed, context-specific errors.
* The `unwrap()` and `expect()` macros are strictly prohibited in library code. Use proper error propagation (`?`) or fallbacks.
* `unwrap()` and `expect()` are only permitted inside test suites (`tests/`).
* The `anyhow` crate is only allowed at executable boundaries (i.e. inside `apps/brain`).

### 3. Safety Boundaries (`unsafe`)
The use of `unsafe` blocks is prohibited unless accompanied by an explicit inline design note (`// SAFETY: ...`) explaining why the compiler's safety invariants cannot be validated at compile time.

### 4. Global State Isolation
Global mutable state (e.g. `static mut` or un-isolated global lazy statics) is forbidden. All shared resources (SQLite Connection Pool, CPython Interpreter, HTTP Clients) must be owned and distributed by the `ResourceManager` in `brain-runtime`.

### 5. Asynchronous Cancellation-Safety
All async futures spawned in the runtime must be cancellation-safe. Loops selecting over futures (`tokio::select!`) must ensure that no state is left corrupted or partially written if a branch is cancelled.

### 6. SQLite Access Boundaries
Direct SQLite or database engine calls (via `rusqlite` or `sqlx`) are strictly prohibited outside the `brain-storage` crate. All other crates must interact with storage via the Repository interfaces exposed through the Service layer.

### 7. CPython/PyO3 Isolation
No reference to `pyo3` or CPython types is allowed outside the `brain-python` crate. Any other crate requesting Python agent execution must utilize the abstract traits (`ChatAgent`, `ExtractionAgent`, etc.) exposed by `brain-core`.

### 8. Long-Running Task Lifecycle Events
Every background task (e.g. edge decay sweep, database backup, or memory consolidation) must emit lifecycle notifications to the Event Bus upon startup, progress checkpoints, and completion/failure.

### 9. Crate-Level Test Ownership
Every crate must own and run its own unit and integration tests locally. All public traits require dedicated integration test coverage.

### 10. API & Struct Documentation
Every public struct, enum, function, and trait in library crates must be documented using Rust doc comments (`///`).

### 11. Security Manifest Validation
The `PluginManager` must run validation tests on every new plugin's `manifest.toml` at startup, ensuring permissions requested match allowed security limits.

### 12. Command & Event Serialization
Commands and events must be serialized using versioned envelopes. Structural modifications require an RFC.

### 13. UI Isolation
The TUI code (`brain-tui`) must run on a dedicated OS thread. It can never call blocking storage queries on the render thread.

## Part 2: Programmatic Architecture Tests

To prevent developers or autonomous agents from violating crate dependency boundaries, the workspace includes a dedicated architecture verification suite in `crates/brain-core/tests/architecture_tests.rs`. This test parses all `Cargo.toml` files in the workspace and asserts that no disallowed dependencies are declared.

```rust
#[cfg(test)]
mod tests {
    use std::fs;
    use std::path::Path;

    fn assert_no_dependency(crate_toml_path: &str, forbidden_dep: &str) {
        let content = fs::read_to_string(crate_toml_path)
            .unwrap_or_else(|_| panic!("Failed to read {}", crate_toml_path));
        
        let target = format!("{} =", forbidden_dep);
        let target_quoted = format!("\"{}\"", forbidden_dep);
        
        assert!(
            !content.contains(&target) && !content.contains(&target_quoted),
            "Architectural Violation: Crate '{}' is forbidden from depending on '{}'.",
            crate_toml_path,
            forbidden_dep
        );
    }

    #[test]
    fn test_dependency_boundaries() {
        // 1. brain-storage cannot depend on brain-tui
        assert_no_dependency("../brain-storage/Cargo.toml", "brain-tui");

        // 2. brain-python cannot depend on brain-storage
        assert_no_dependency("../brain-python/Cargo.toml", "brain-storage");

        // 3. brain-domain cannot depend on any other crate
        assert_no_dependency("../brain-domain/Cargo.toml", "brain-core");
        assert_no_dependency("../brain-domain/Cargo.toml", "brain-storage");
        assert_no_dependency("../brain-domain/Cargo.toml", "brain-python");
        assert_no_dependency("../brain-domain/Cargo.toml", "brain-runtime");
    }
}
```

## Part 3: Incremental Migration Plan

Every task is structured as a standalone Pull Request (PR) to keep reviews simple, focused, and reversible.

### Global Acceptance Criteria
A migration task (PR) is **Done** if and only if it meets all of the following criteria:
* `✓` `cargo nextest run` passes with zero failures.
* `✓` `cargo clippy --all-targets -- -D warnings` compiles without warnings.
* `✓` `cargo fmt --check` verifies formatting is clean.
* `✓` All integration tests pass successfully.
* `✓` Benchmark regression is `< 5%` (validated via Criterion execution).
* `✓` Crate documentation is fully updated in its local `README.md`.

---

### Implementation Order
To ensure a stable baseline, developers and agents must execute tasks in this sequence:
1. **Initialize Workspace & CI:** Configure Cargo crates and verify CI (PR-001).
2. **Setup Domain & Domain Verification:** Populate entities and add architecture validation tests (PR-002, PR-003, PR-004, PR-005).
3. **Persist & Config:** Build config engines and database drivers (PR-006 to PR-010).
4. **Cache & Business Services:** Build STM caches and service layers (PR-011 to PR-014).
5. **Dynamic Extension, PyO3 & Tools:** Encapsulate Python interpreter and tool registries (PR-015 to PR-018).
6. **Task scheduling, TUI & apps integration:** Build Ratatui console and coordinate v2 app (PR-019 to PR-022).
7. **Verification & Single Release Deprecation:** Validate parity of v2, release, and deprecate old `/cli` and `/daemon` monoliths (PR-023, PR-024).
