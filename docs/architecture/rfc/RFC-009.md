## 1. Executive Summary

Projections (defined in RFC-008) provide read-only representations of static semantic state. However, Brain is a live runtime—background consolidation tasks run, relationship weights decay, reflection passes execute, and external adapters stream new observations. To ensure presentation layers (such as terminal frontends, ACP socket connections, or external agent plugins) remain responsive without polling or blocking, Brain requires a standardized event-driven model.

This RFC defines the runtime semantics for how change is communicated. It separates domain events (durable business facts) from operational lifecycle events (transient runtime transitions) and progress tracking (how long-running tasks publish their internal execution metadata). Following Brain's architectural philosophy, this model completely excludes presentation details (Ratatui canvas, colors, widgets), focusing entirely on backend event semantics.

## 2. Affected Subsystems

- `crates/brain-core`: Defining the shared event trait interfaces, progress structures, task lifecycle states, and initial memory dispatchers.
- `crates/brain-services`: Emitting runtime events and updating progress states during reflection, compilation, and compaction.
- Presentation Adapters (TUI, ACP, A2A): Subscribing to event streams and adapting presentation based on operational state.

## 3. Proposal Details

### A. Event Taxonomy & Traits
Rather than using a giant centralized enum, events are classified into distinct structural groups bound together by a general event trait. This prevents the event dispatcher from devolving into a massive, monolithic switch block as the runtime evolves.

```
                     ┌───────────────────────┐
                     │     RuntimeEvent      │  (Base Trait)
                     └───────────┬───────────┘
                                 │
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
   Domain Events          Lifecycle Events       Projection Events
  - Durable facts        - Ephemeral status     - Invalidation signals
  - Persisted in store   - Task state machine   - Cache clears
```

1.  **Domain Events (Durable)**: Immutable, historical facts capturing state mutations inside domain aggregates. Persisted in the event store (LTM) for auditability and recovery.
    *   *Examples*: `MemoryMerged`, `RelationshipCreated`, `RelationshipStrengthened`.
    *   *Serialization note*: Any signatures in this document utilizing strings or placeholders for domain events are purely illustrative. Domain events are structured, strongly-typed domain-native models.
2.  **Lifecycle Events (Ephemeral)**: Operational state changes describing the execution state of runtime operations. They are not persisted to database storage and are managed strictly in memory. They represent any running computation segment (synchronous operations, background processes, remote commands, scheduled jobs, or event replays).
    *   *Examples*: `OperationStarted`, `OperationFailed`, `EngineInitialized`.
3.  **Projection Events (Ephemeral)**: Signals indicating that the underlying semantic model has mutated, rendering one or more cached **Projection Instances** dirty.
    *   *Examples*: `ProjectionInstanceInvalidated`.

---

### B. Background Task Lifecycle & Progress Metadata
Long-running background operations (such as model compaction, graph compiles, or Python FFI semantic extractions) proceed through a deterministic state machine:

```
    ┌───────────┐      ┌───────────┐      ┌───────────┐
    │  Created  ├─────►│  Started  ├─────►│Progressing│
    └───────────┘      └─────┬─────┘      └─────┬─────┘
                             │                  │
         ┌───────────────────┼──────────────────┤
         ▼                   ▼                  ▼
   ┌───────────┐       ┌───────────┐      ┌───────────┐
   │ Cancelled │       │  Completed│      │  Failed   │
   └───────────┘       └───────────┘      └───────────┘
```

*   **Created**: Task is registered with the runtime coordinator, carrying an `OperationId` and a parent `CorrelationId`.
*   **Started**: Task execution begins on a worker thread pool.
*   **Progressing**: Task streams operational progress events containing current execution metadata.
*   **Completed**: Task finishes successfully, yielding optional output metadata (which invalidates target projection instances if applicable).
*   **Failed**: Task terminates due to an error, returning an error envelope.
*   **Cancelled**: Task execution is aborted by a user or external supervisor command.

*Note on Progress*: Progress is **metadata about runtime execution** rather than a distinct event class. Real-time progress stats (semantic stages and progress ratios) are embedded directly within the lifecycle event payload during the `Progressing` state.

### C. Event Source & Observability

Every lifecycle and operational event must declare its originating system module via `EventSource`. This ensures that logging, telemetry, and debugging systems can trace precisely which subsystem triggered an update.

```rust
pub enum EventSource {
    Domain,
    Projection,
    Reflection,
    Compaction,
    Ingestion,
    Adapter,
    Scheduler,
}
```

### D. Event Semantics & Invariants
1.  **Durable vs. Ephemeral Boundaries**: Domain events are append-only and durable. Operational, progress, and projection events are ephemeral and fire-and-forget.
2.  **Scoped Monotonic Ordering**: Ephemeral progress and operational events emitted within a task stream must carry incrementing sequence numbers. Sequence numbers are **monotonic strictly within a single `OperationId` namespace** (representing a single task execution), preventing unnecessary global coordination.
3.  **Trace Correlation**: Every operational event must carry both:
    *   `OperationId`: Uniquely identifies exactly one specific execution run of a task.
    *   `CorrelationId`: Traces the causal origin of the execution tree (e.g. a single user command or adapter run that triggered observation -> extraction -> reflection -> projection).
4.  **No Representation in Domain**: Events inside `brain-domain` represent business rules. Operational progress and presentation lifecycle states are strictly prohibited from entering domain aggregates.
5.  **Event Immutability**: Once emitted by any runtime component, an event is strictly immutable and must never be modified in place.
6.  **Event Schema Versioning**: Event schemas are versioned independently from transport protocols, ensuring backward compatibility as the runtime evolves.

## 4. The Progress Model

Percentages are brittle and misleading for open-ended AI extraction and graph compaction tasks. Brain prioritizes **Semantic Stages** as the primary progress abstraction, only using optional completion ratios when the underlying dataset size is statically bounded.

### A. Semantic Stages
Background tasks communicate their current execution boundary using defined lifecycle stages:
1.  **Observation**: Parsing inputs, reading raw socket streams, or locking files.
2.  **Extraction**: Running NLP parsing, vectorizing inputs, or isolating semantic nodes.
3.  **Synthesis**: Identifying duplicates, aligning entity models, and resolving naming conflicts.
4.  **Reflection**: Re-evaluating relationship decay weights and executing graph clustering algorithms.
5.  **Projection**: Rebuilding and updating downstream view models.

### B. Optional Ratios
For tasks with known sizes (e.g. indexing 1,000 files), progress metadata may attach progress metrics:
```rust
struct ProgressRatio {
    pub completed: usize,
    pub total: usize,
}
```
If the total size is unknown, the progress metadata omits the ratio and relies solely on the `SemanticStage`.

## 5. Subscription & Dispatch Model

```
 ┌────────────────────────────────────────────────────────┐
 │                   Background Runner                    │
 └───────────────────────────┬────────────────────────────┘
                             │ (mpsc channels)
 ┌───────────────────────────▼────────────────────────────┐
 │                  Unified dispatcher                    │ (Services / Core)
 └───────────────────────────┬────────────────────────────┘
                             │
            ┌────────────────┼────────────────┐
            ▼                ▼                ▼
       [TUI Adapter]   [ACP Adapter]    [Logger Adapter]
```

*   **Deferred Crate Boundaries**: We intentionally defer a dedicated `brain-events` crate. Initially implement the event dispatch infrastructure inside `brain-core` or `brain-services`, and extract a standalone `brain-events` crate only if system scale and lifecycle complexity grow to justify the additional boundary.
*   **Bounded Channels**: Adapters subscribe to the event dispatcher via bounded multi-producer, single-consumer (`mpsc`) channels.
*   **Back-pressure Strategy**:
    *   If a presentation adapter lag occurs, the dispatcher **discards ephemeral progress and runtime events** to prevent blocking the core background worker threads.
    *   **Domain events** are never discarded; if the channel fills, the runtime blocks or buffers domain events up to a set capacity to guarantee data safety.
*   **Replay Limits**: Ephemeral events cannot be replayed. Domain events can be replayed from the persistent SQLite event log to reconstruct active state.

## 6. API Contracts

We define the following type structures inside `crates/brain-core/src/event.rs`.

### Rust Crate Signature Changes

```rust
// crates/brain-core/src/event.rs

use serde::{Serialize, Deserialize};
use std::time::SystemTime;
use brain_domain::id::EpochId;

/// Monotonic IDs for correlation and task tracing.
pub type OperationId = uuid::Uuid;
pub type CorrelationId = uuid::Uuid;

/// Base trait representing any event flowing through the runtime.
pub trait RuntimeEvent: Send + Sync + 'static {}

/// Subsystems that can emit events.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub enum EventSource {
    Domain,
    Projection,
    Reflection,
    Compaction,
    Ingestion,
    Adapter,
    Scheduler,
}

/// High-level semantic stages for knowledge processing.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub enum SemanticStage {
    Queued,
    Observation,
    Extraction,
    Synthesis,
    Reflection,
    Projection,
    Finalizing,
}

/// State machine boundaries for background tasks.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub enum TaskState {
    Created,
    Started,
    Progressing {
        stage: SemanticStage,
        completed_items: Option<usize>,
        total_items: Option<usize>,
    },
    Completed,
    Failed(String),
    Cancelled,
}

/// Ephemeral operational metadata for long-running processes.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct TaskProgress {
    pub operation_id: OperationId,
    pub correlation_id: CorrelationId,
    pub state: TaskState,
    pub source: EventSource,
    pub sequence: u64,
    pub timestamp: SystemTime,
}

impl RuntimeEvent for TaskProgress {}

/// Signal to invalidate projection instances.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ProjectionInstanceInvalidatedEvent {
    pub projection_type: String,
    pub epoch: EpochId,
    pub source: EventSource,
    pub correlation_id: CorrelationId,
}

impl RuntimeEvent for ProjectionInstanceInvalidatedEvent {}
```

## 7. Design Alternatives Evaluated

We compare two models for dispatching progress:

| Alternative | Description | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **Option A**<br/>(Stage-Based Push Events) | Workers push structured `TaskProgress` events containing active semantic stages over the event bus. | • Extremely lightweight.<br/>• Zero lock contention.<br/>• Decouples task logic from UI layout. | • Presentation layer must maintain its own state trackers to aggregate task history. |
| **Option B**<br/>(Central Task Registry) | A thread-safe, shared global registry where workers register handles and update a shared state struct. | • Easy for presentation layers to query the active states in one call. | • Introduces lock contention on the global registry lock.<br/>• Violates unidirectional event flow. |

### Recommendation
**Option A (Stage-Based Push Events)** is recommended. It maps directly to our protocol-independent architecture, operates under low lock contention, and naturally scales to support streaming over Unix Domain Sockets (UDS) to external client adapters (ACP/MCP) without polling.

## 8. Verification & Testing Plan

### Automated Tests
- **State Machine Invariant Verification**: Unit tests asserting that task transition events proceed in correct sequence (e.g. asserting `Started` cannot follow `Completed`).
- **Back-pressure Safety**: Integration tests simulating slow clients and asserting that the dispatcher successfully drops ephemeral progress events without crashing or blocking the worker threads.
- **Trace Correlation Verification**: Tests confirming that nested subtasks correctly propagate their parent `CorrelationId` and unique `OperationId` down the event stream.
