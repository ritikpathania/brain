# RFC-005: Adapter Lifecycle

**Author:** Antigravity & USER  
**Date:** 2026-06-29  
**Status:** Proposed  
**Reference RFCs:** RFC-001 (Event Ingestion Platform), RFC-002 (Unified IPC Protocol)

---

## 1. Executive Summary

This RFC defines the unified **Adapter Lifecycle** for client integrations connecting to the Brain daemon. As the system moves from standalone scripts to persistent tools (such as IDE extensions and daemon adapters), it is critical to govern how clients identify themselves, negotiate versions/capabilities, verify client/server liveness, and teardown resources cleanly.

By establishing a structured, state-driven lifecycle handshake, a diagnostic heartbeat protocol, and graceful shutdown semantics, we secure the interface boundary across all client implementations.

- `crates/brain-integrations` (JSON Schemas, serialization models)
- `crates/brain-sdk-rs` (handshake, heartbeat timers, and shutdown commands)
- `sdks/python` (handshake, shutdown, and validation tests)
- `daemon` (UDS server connection manager, liveness tracker, and adapter state)

## 3. Proposal Details

We propose a three-stage lifecycle for all adapters: **Negotiate**, **Maintain**, and **Teardown**.

```text
Adapter                           Daemon
   │                                 │
   │ 1. HandshakeRequest (JSON)      │ [State: Connecting]
   ├────────────────────────────────>│ Verify capabilities & version
   │                                 │
   │ 2. HandshakeResponse (JSON)     │ [State: Connected]
   |<────────────────────────────────┤ Connection ID generated
   │                                 │
   │ 3. HeartbeatRequest (Status)    │ [State: Ready]
   ├────────────────────────────────>│ (Interval-based)
   │ 4. HeartbeatResponse            │
   |<────────────────────────────────┤
   │                                 │
   │ 5. DisconnectRequest (JSON)     │ [State: Closing]
   ├────────────────────────────────>│ Clean up session state
   │                                 │
   ▼                                 ▼
```

### 3.1 Handshake & Capability Negotiation

Upon initial connection over the UDS/TCP socket, the adapter must send a `HandshakeRequest` as its first newline-delimited JSON frame. No other commands will be accepted by the daemon prior to a successful handshake.

The handshake establishes:
- **Connection and Session Identity**: Explicit connection, adapter, and session IDs.
- **Protocol Version Negotiation**: Asserting supported versions of the wire format.
- **Capability Negotiation**: Resolving supported ingestion formats (e.g., `ConversationMessages`, `WorkspaceFiles`).
- **Feature Negotiation**: Opting into/out of server-side capabilities (e.g. `Batching`, `Replay`).

### 3.2 Heartbeat & Operational Diagnostics

To prevent resource leakage from orphaned sockets (especially common in IDE crashes), the client must periodically transmit a `HeartbeatRequest`. Rather than a simple ping-pong, this packet contains crucial client diagnostics:
- `last_ack_sequence`: The highest event sequence successfully acknowledged by the daemon.
- `queue_depth`: The number of events currently buffered in the SDK queue.
- `pending_batches`: The number of batches currently awaiting transmission.
- `uptime_ms`: The duration the adapter client has been running.

The daemon responds with a `HeartbeatResponse` containing similar daemon metrics (e.g., server uptime, memory usage, or congestion indicators).

### 3.3 Graceful Shutdown

When an adapter terminates cleanly (e.g., VS Code extension deactivation, script exit), it must transmit a `DisconnectRequest` containing:
- `reason`: Clean exit, crash, reload, or dependency update.
- `last_sent_sequence`: The sequence number of the final transmitted event.

Upon receipt, the daemon flushes pending pipelines for that connection ID and closes the socket cleanly.

## 4. Contract Changes (Interfaces & Types)

### 4.1 JSON Schema Definition

Both SDKs and the daemon will validate against versioned JSON schemas located at `protocol/schema/v1/`:

#### `handshake.schema.json`
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "HandshakeRequest",
  "type": "object",
  "required": ["protocol_version", "connection_id", "adapter_id", "session_id", "capabilities"],
  "properties": {
    "protocol_version": { "type": "string", "enum": ["1.0"] },
    "connection_id": { "type": "string", "format": "uuid" },
    "adapter_id": { "type": "string" },
    "session_id": { "type": "string" },
    "capabilities": {
      "type": "array",
      "items": { "type": "string" }
    },
    "supported_schema_versions": {
      "type": "array",
      "items": { "type": "string" }
    }
  }
}
```

#### `heartbeat.schema.json`
```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "HeartbeatRequest",
  "type": "object",
  "required": ["last_ack_sequence", "queue_depth", "pending_batches", "uptime_ms"],
  "properties": {
    "last_ack_sequence": { "type": "integer", "minimum": 0 },
    "queue_depth": { "type": "integer", "minimum": 0 },
    "pending_batches": { "type": "integer", "minimum": 0 },
    "uptime_ms": { "type": "integer", "minimum": 0 }
  }
}
```

### 4.2 Protocol Compatibility Policy

Protocol evolution must comply with the following structural compatibility table:

| Change             | Minor | Major | SDK Action |
| ------------------ | :---: | :---: | ---------- |
| Add optional field |   ✅   |   —   | Ignored by older clients |
| Add event type     |   ✅   |   —   | Handled/Logged cleanly by older clients |
| Remove field       |   ❌   |   ✅   | Fails validation |
| Rename field       |   ❌   |   ✅   | Fails validation |
| Change semantics   |   ❌   |   ✅   | Requires major protocol bump |

---

## 5. Backward Compatibility Plan

- **Unknown Fields**: Both SDKs must ignore unrecognized JSON properties during deserialization.
- **Unknown Event Types**: Adapters and daemon must handle unknown event variants gracefully by logging/rejecting cleanly instead of panicking.
- **Legacy Fallback**: If a client does not send a `HandshakeRequest` as the first line and instead sends a legacy event, the daemon will log a warning and fallback to a default capability profile.

---

## 6. Verification & Testing Plan

### 6.1 Schema Validation of Fixtures
A validation step runs *prior* to SDK testing. It checks that all positive fixtures match the JSON schemas, and all negative fixtures fail them, preventing test pollution from incorrect fixtures.

### 6.2 byte-for-byte Serialization Round-trip
Both SDKs must pass the canonical round-trip assertion:
```text
deserialize(Fixture) -> serialize(Struct) -> compare_bytes(Fixture, Output)
```

### 6.3 Diagnostic Heartbeat Verification
Integration tests will assert:
- Periodic heartbeat triggers.
- Correct heartbeat metadata (e.g. queue depth reflects current buffer size).
- Daemon deallocates socket state if heartbeats are missed beyond the timeout.
