## 1. Executive Summary

This RFC establishes the **Brain Terminal UX Specification** as the canonical frontend styling, interface interaction, and component behavior contract for all terminal-based Brain clients.

As the memory companion moves toward stable production releases, it is critical to secure the frontend client (`crates/brain-tui`) with the same level of architectural rigor applied to the storage and event schemas. This specification links our user-interface design to 7 core UX principles, details layout breakpoints, defines design tokens, and specifies fallbacks for restricted terminals.

9. **[Theming Specification](../../design/THEMING.md)**: Semantic style tokens and contrast ratios.

13. **[Terminal Capabilities](../../design/TERMINAL_CAPABILITIES.md)**: Graceful feature degradation (RGB vs ANSI, Unicode vs ASCII).
14. **[Performance Budget](../../design/PERFORMANCE_BUDGET.md)**: Maximum latencies (Startup < 20ms, Render < 5ms, Streaming < 10ms).
15. **[Extension Philosophy](../../design/EXTENSION_PHILOSOPHY.md)**: Guidelines for adding components without bloating the core.

## 4. Contract Changes (Interfaces & Types)

This specification mandates that the client `Theme` mappings (such as defined in `crates/brain-tui/src/ui/theme.rs`) and layout partitions (defined in `crates/brain-tui/src/ui/renderer.rs`) remain strictly decoupled:

### 4.1. Theme Tokens Protocol
Clients must load styles using the semantic color tokens rather than calling raw RGB colors directly inside widgets:
```rust
pub struct Theme {
    pub primary: Style,
    pub secondary: Style,
    pub accent: Style,
    pub muted: Style,
    pub success: Style,
    pub warning: Style,
    pub error: Style,
    pub thinking: Style,
    pub streaming: Style,
    pub user: Style,
    pub assistant: Style,
    pub tool: Style,
    pub system: Style,
}
```

### 4.3. State Projection Boundary (Decoupled Presentation Model)
To minimize coupling between the domain state machine and presentation rendering:
1. The **State Reducer** does not talk directly to the widgets.
2. It reduces user input and network events into an immutable **ViewModel** (representing presentation states like `ConversationView`, `StatusBarView`, `SidebarView`, `DialogView`).
3. The **Renderer** consumes these immutable view models and translates them into stateless widget trees using semantic theme styles.

## 5. Backward Compatibility Plan

Since this RFC governs presentation, styling, and user-interaction interfaces, it has **zero impact** on:
- Underlying UDS IPC communication schemas (negotiated in RFC-002).
- SQLite/DuckDB relational database migrations (governed by `brain-storage`).
- Event envelopes and ingestion packets (governed by RFC-001).

## 6. Verification & Testing Plan

### 6.1. Unit and Integration Verification
Any TUI modification must pass automated visual unit tests verifying that state projection and viewmodels compute correctly without runtime heap allocations:
```bash
PYO3_PYTHON=$(pwd)/daemon/.venv/bin/python cargo test -p brain-tui
```

### 6.2. Golden Snapshot Verification
To prevent visual layout and style regressions, the client verification suite includes automated **Golden Snapshot Tests** comparing rendered terminal buffers against pre-recorded mock expectations. 

Visual assertions must be target-tested by splitting snapshot checks into granular directories:
* `tests/golden/components/`: Snapshots for rendering primitives (`divider.snap`, `spinner.snap`, `progress.snap`).
* `tests/golden/widgets/`: Snapshots for stateless component widgets (`sidebar.snap`, `dialog.snap`, `status.snap`).
* `tests/golden/screens/`: Snapshots for full viewport compositions (`chat.snap`, `welcome.snap`, `history.snap`).
* `tests/golden/themes/`: Color assertions for all themes (`dark.snap`, `light.snap`, `ansi.snap`, `daltonized.snap`).
* `tests/golden/responsive/`: Sizing assertions under different width bounds (`60cols.snap`, `80cols.snap`, `120cols.snap`, `160cols.snap`).

### 6.3. Performance Budget Auditing
Rather than treating performance budgets as rigid constants, budgets scale dynamically from baseline measurements:
1. **Target**: Initial targets (e.g., startup `< 20ms`, render time `< 5ms`, streaming latency `< 10ms`).
2. **Benchmark**: Concrete micro-benchmark metrics run locally on a release build.
3. **CI Threshold**: Auto-enforced regression limit set at **+15%** over measured benchmarks. If a PR exceeds this margin, the CI pipeline triggers a build failure.
