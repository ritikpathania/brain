# RFC-003: Brain Knowledge Format (BKF) Specification

**Status:** PROPOSED  
**Precedence:** Canonical Knowledge Interchange Format  

---

## 1. Executive Summary

This RFC introduces the **Brain Knowledge Format (BKF)** as the canonical internal representation of all knowledge inside Brain. 

BKF acts as the common interchange format between various parsing ingestion sources (Markdown, PDF, Notion, Slack, Git, etc.) and downstream operations (chunking, entity/relationship extraction, vector indexing, graph construction, storage, and retrieval).

BKF is a domain model, not a storage schema. It decouples parser/plugin-specific formats from Brain's core retrieval and indexing pipeline.

---

## 2. Motivation

Currently, as ingestion sources expand, downstream storage and retrieval logic risk tight coupling to parser-specific ASTs or custom DTOs. 

By standardizing on a single, canonical intermediate format (BKF), we guarantee that:
1. **Source Agnosticism**: The retrieval, storage, and reasoning layers do not care about the origin of the knowledge (e.g. email vs. code file vs. wiki page).
2. **Pipeline Decoupling**: Parsing changes do not ripple into vector search, database persistence, or graph reasoning layers.
3. **Streamlined Normalization**: Every plugin compiles its input into a raw AST that is subsequently normalized into structured BKF elements via a centralized validation pipeline.

---

## 3. Design Invariants

All extensions or usage of the BKF model must adhere to these 10 invariants:

1. **Single Canonical Representation**: BKF is the sole canonical semantic knowledge representation format inside Brain.
2. **No Storage Leakage**: BKF never stores implementation-specific storage details (such as SQLite row IDs, relational primary/foreign key mappings, or table structures).
3. **No Retrieval Leakage**: BKF never stores retrieval-specific runtime states (like search scores, relevance ranks, or execution contexts).
4. **No Provider/LLM Leakage**: BKF remains provider-agnostic, storing zero provider-specific flags or model prompt configurations.
5. **Immutability**: Once constructed, a `BKFDocument` is strictly immutable (read-only) to prevent accidental mutation side-effects during concurrent pipeline reasoning.
6. **Strict Type Safety**: All linkages, references, and associations between elements must utilize strongly-typed identifiers (sortable chronological ULIDs).
7. **Correctness by Construction**: A `BKFDocument` cannot be instantiated without passing through the `BKFDocumentBuilder`, which enforces strict structural referential integrity and acyclic hierarchies.
8. **Projection Decoupling**: Derived artifacts (such as vector embeddings, lexical BM25 indexes, graph indexes, or caches) are downstream projections of the canonical document, never owned by BKF itself.
9. **Deterministic Serialization**: Two semantically identical BKF documents must serialize to identical byte-level layouts. This guarantees consistent cryptographic hashing, caching, signatures, and synchronization.
10. **Runtime State Isolation**: Retrieval and execution layers must never mutate or decorate BKF models with runtime values (e.g. search scores, context weights). Such states must be managed separately.

---

## 4. Architectural Boundaries and Ownership

To maintain architectural purity, boundaries are established as follows:

| Component | Responsibility / Ownership |
|-----------|----------------------------|
| **BKF (`brain-domain::bkf`)** | Owns the canonical, pure, in-memory domain structures and validation constraints. |
| **Ingestion Plugins** | Parse external streams and emit parser-specific ASTs. |
| **Normalization Pipeline** | Normalizes parser-specific ASTs into `BKFDocumentBuilder` statements. |
| **Storage (`brain-storage`)** | Maps and persists BKF models into SQLite or other database engines. |
| **Embeddings** | Generates vectors and stores links referencing BKF identifiers. |
| **Retrieval** | Consumes BKF structures to answer user questions or compile prompts. |
| **LLMs** | Consume parts of BKF objects for semantic understanding and text generation. |

---

## 5. Specification & Schema Definitions

The modular design splits the model into discrete files under `crates/brain-domain/src/bkf/`:

### 5.1. Strongly Typed Identifiers (`ids.rs`)
Identifiers are wrapped sortable ULIDs to guarantee chronologically ordered IDs that prevent naming clashes across standard system domain identifiers:
* `BkfDocumentId`
* `BkfSectionId`
* `BkfBlockId`
* `BkfEntityId`
* `BkfRelationshipId`
* `BkfFactId`
* `BkfCitationId`
* `BkfAttachmentId`

### 5.2. Extensible Provenance Chain (`provenance.rs`)
Knowledge objects reference a chain (`Vec<Provenance>`) of origins to support nested derivations (e.g. Markdown -> Git Commit -> Filesystem -> Imported Zip -> Web Page):
* `MarkdownFile`
* `Slack`
* `Email`
* `Git`
* `Filesystem`
* `Notion`
* `Web`
* `Custom`

### 5.3. Immutable Document & Builder (`document.rs`, `builder.rs`)
The `BKFDocument` is structured with private fields and public getters:
* `metadata`: Complete metadata containing fingerprint, checksum, license, language, size, created/modified timestamps, and extra parameters.
* `sections`: Ordered, nested tree hierarchy representing the structural sections of the document.
* `blocks`: Contiguous structural content units (Paragraphs, Headings, Code blocks, Tables, Lists, Quotes, Images, or custom data payloads).
* `entities`: Extracted semantic concepts (Person, Org, Function, etc.).
* `relationships`: Directed associations between any BKF elements using a `BKFTargetRef` enum.
* `facts`: Rich, RDF-like statements representing `subject -> predicate -> object` assertions, where subjects are `BKFTargetRef` and objects can be literals, entities, numbers, booleans, or dates.
* `capabilities`: Flag sets (`BKFCapabilities`) advertising present elements to skip expensive searches (e.g., `.capabilities().has_entities`).

---

## 6. Normalization & Validation Flow

To ensure structural correctness, builder compilation enforces:
1. **Uniqueness**: No duplicate IDs are permitted across sections, blocks, entities, relationships, facts, citations, or attachments.
2. **Referential Integrity**: All target references (`BKFTargetRef`) pointing to elements within relationships, facts, or section structures must resolve to existing items within the document.
3. **No Self-Links**: Directed relationships cannot have identical source and target identifiers.
4. **Acyclic Hierarchy**: The section-to-parent hierarchy tree must form a Directed Acyclic Graph (DAG) with no cyclic loops.
