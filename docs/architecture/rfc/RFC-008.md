# RFC-008: Projection Architecture

**Author:** Antigravity AI  
**Date:** 2026-07-16  
**Status:** Implemented  
**Reference RFCs:** [RFC-001](RFC-001.md) / [RFC-002](RFC-002.md) / [RFC-007](RFC-007.md)

---

## 1. Executive Summary

As Brain shifts toward a hexagonal, protocol-independent design, the separation between core semantic knowledge and transport-specific interfaces must be rigidly enforced. Brain's architectural philosophy dictates that:
1. **Semantic knowledge is canonical.**
2. **Presentation is a projection of runtime state, never business logic.**

This RFC introduces **Projections** as a first-class architectural concept within the Brain runtime. A Projection is a read-only, semantic representation of canonical knowledge tailored for specific presentation layers or view states. Rather than letting individual transport adapters query the database or domain layer arbitrarily, this RFC establishes a clean boundary: the runtime defines and executes projections, while transport adapters consume and render them.

---

## 2. Affected Subsystems

This RFC impacts the core service boundary and presentation layers:
- `crates/brain-core`: Defining projection interfaces, projection queries, and capability traits.
- `crates/brain-services`: Implementation of projection mapping, projectors, and caching.
- Presentation Adapters (TUI, CLI, ACP, MCP, A2A): Refactoring transport layers to consume structured projections instead of querying raw domain models directly.

## 3. Proposal Details

### A. Core Concepts & Decoupling
To achieve protocol independence, the data pipeline is structured to separate semantic views from wire-level serialization:

```
Canonical Knowledge (Graph)
            │
            ▼
   Semantic Projection  (A structured, read-only representation of a graph slice)
            │
            ▼
   Serialization Schema (One or more serialization contracts, e.g., JSON, ViewModel)
            │
            ▼
    Transport Adapter   (Final presentation mapping, e.g., ACP Socket, TUI Canvas)
```

A Projection is a functional transformation of the canonical semantic graph $G$ at state $t$, parameterized by a typed context $C$:

$$P = \pi(G_t, C)$$

*   **Read-Only**: Projections contain no mutating logic. Any state alteration must proceed via the domain's Command interface.
*   **Decoupled Serialization**: A projection defines structural types (e.g. `MemoryListView`, `GraphNeighborhoodView`) but remains entirely agnostic of serialization details (e.g., JSON string templates, ANSI escape sequences, HTML syntax, or transport headers).
*   **Decoupled Execution**: The calling layer does not specify execution execution policy (such as synchronous vs. asynchronous execution, or cache lookup). The projection service manages caching, thread boundaries, and database query scheduling internally, presenting a unified, non-blocking interface to consumers.

Additionally, the runtime distinguishes between a **Projection Type** and a **Projection Instance**:
*   **Projection Type/Definition**: The blueprint defining the static mapping structure (e.g., `MemoryListProjection`).
*   **Projection Instance**: The concrete projection result produced by executing a Projection Type against a specific graph snapshot $G_t$ and parameterized query context $C$ (e.g., `MemoryListProjection` computed with `limit = 20` at `Epoch(5)`). Caching, subscription updates, and invalidation rules operate strictly on the instance level.


### B. Core Architectural Invariants

Every projection implementation in the runtime must satisfy the following invariants:

1.  **Idempotence**: For any static state $G_t$ and parameter context $C$, the projection function must yield identical output:
    $$\pi(G_t, C) \equiv \pi(G_t, C)$$
2.  **Temporal Consistency**: Every projection must align with a single transaction epoch or compaction generation of the canonical graph. It cannot merge data across uncommitted states.
3.  **Transport Independence**: Projections define logical view structures. They must not depend on physical client concepts (such as font metrics, layout width bounds, terminal themes, or adapter sockets).
4.  **No Leaked Business Logic**: Projections are passive data structures. They cannot execute domain validation, calculate relationship strength decay, or evaluate reflection metrics.
5.  **Completeness**: A projection must completely represent the requested semantic slice. It must not silently omit knowledge due to downstream presentation constraints. Any filtering, pagination, or truncation must be explicitly requested via the query parameters in the projection context.
6.  **Determinism**: Projection sorting, ordering, and structure must be stable and reproducible. The output must be free of hidden timestamps, randomness, or iteration-order dependency (e.g. hash map iteration must be sorted deterministically to prevent erratic UI changes).

### C. Execution Model & Ownership
*   **Service-Layer Ownership**: Projectors are **application services**, not domain services. Projections represent derived views and belong in the application service or facade layer, keeping the domain entities free of presentation concerns.
*   **Decoupled Call Routing**: The projection service abstracts whether a query is served synchronously (via in-memory caches or STM lookups) or asynchronously (offloaded to thread pools via `tokio::task::spawn_blocking` to avoid stutters on sqlite reads).

## 4. Contract Changes (Interfaces & Types)

To establish projection capability, we define the core `Projector` trait, context container, and view structures inside `crates/brain-core/src/projection.rs`.

### Rust Crate Signature Changes

```rust
// crates/brain-core/src/projection.rs

use serde::{Serialize, Deserialize};
use brain_domain::id::EpochId;

/// Defines consistency expectations for projection queries.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ConsistencyMode {
    /// Read volatile memory cache (fastest, eventually consistent, may not be persisted yet).
    Volatile,
    /// Read strictly persisted database transaction (strong consistency with durable storage).
    Strong,
}

/// Mark marker trait for projection parameters to ensure type safety.
pub trait ProjectionQuery: Send + Sync + 'static {}

/// Unified context passed to projectors, allowing extension without breaking APIs.
pub struct ProjectionContext<'a, Q: ProjectionQuery> {
    /// Monotonic epoch representing source graph version.
    pub epoch: EpochId,
    /// Type-safe query filters or sub-graph traversal boundaries.
    pub query: &'a Q,
    /// Consistency constraint for database vs. volatile memory reads.
    pub consistency: ConsistencyMode,
}

/// Core interface for projection execution.
pub trait Projector<P, Q: ProjectionQuery> {
    type Error: std::error::Error + Send + Sync + 'static;

    /// Generates the semantic projection from the provided context.
    /// Execution policies (e.g. caching, tokio threads) are handled internally.
    fn project(&self, ctx: &ProjectionContext<'_, Q>) -> Result<P, Self::Error>;
}

/// Event payload indicating a previous projection snapshot is no longer valid.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ProjectionInvalidatedEvent {
    pub projection_type: String,
    pub epoch: EpochId,
}
```

Example semantic view models projected for consumers:

```rust
// crates/brain-domain/src/views/memory.rs

use serde::{Serialize, Deserialize};
use brain_domain::id::MemoryId;
use brain_core::projection::ProjectionQuery;

/// Explicit query parameters for the memory list.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct MemoryListQuery {
    pub limit: usize,
    pub offset: usize,
    pub filter_tag: Option<String>,
}

impl ProjectionQuery for MemoryListQuery {}

/// Flat projection of memories optimized for list presentation.
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct MemoryListProjection {
    pub items: Vec<MemoryItemProjection>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct MemoryItemProjection {
    pub id: MemoryId,
    pub short_summary: String,
    pub age_decay_percentage: f32,
    pub relationship_count: usize,
    pub timestamp: i64,
}
```

## 5. Design Alternatives Evaluated

We compare three approaches to implementing this architecture:

| Alternative | Implementation | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **Option A**<br/>(Dedicated Projection Engine) | A standalone crate (`brain-projection`) containing specialized query parsers, state builders, and cache pools. | • Maximum encapsulation.<br/>• High logic reuse between CLI, TUI, and ACP.<br/>• Easy to unit test in isolation. | • Adds crate compilation overhead.<br/>• More complex initialization wiring. |
| **Option B**<br/>(Service-Layer Capability) | Projectors implemented as traits/services directly inside `brain-services`, using existing database/graph interfaces. | • Clean, incremental path.<br/>• Reuses existing service dependency graphs.<br/>• Zero new crate overhead. | • Bypassing is possible (adapters might still call underlying repositories directly). |
| **Option C**<br/>(Transport-Owned Adapters) | Let transport adapters query repositories and format the raw entities themselves. | • Simple to implement initially.<br/>• Highly localized. | • Code duplication.<br/>• Violates presentation invariants.<br/>• Harder to enforce threading safety across different protocols. |

### Recommendation
**Option B (Service-Layer Capability)** is recommended for the initial implementation. We intentionally defer a dedicated projection subsystem (Option A) until projection complexity exceeds the capabilities of the existing service layer. Premature extraction would increase architectural surface area without providing proportional benefit. Option B enforces the semantic projection boundary inside `brain-services` while allowing us to migrate adapters cleanly.

## 6. Backward Compatibility Plan

*   **Data Models**: Projections are transient, derived structures and do not persist data. SQLite schema migrations are unaffected.
*   **API Protocol**: Legacy JSON responses will be deprecated in favor of versioned projection schemas. To support transition, older adapters can consume legacy mappings implemented as deprecated projection adapter views.

## 7. Verification & Testing Plan

### Automated Tests
- **Deterministic Assertions**: Unit tests verifying that identical graph states and context parameters generate identical projection struct states, specifically checking sorting stability.
- **Async Safety Checks**: Integration tests checking that projecting during concurrent writes does not block the executor or yield corrupted records (asserting epoch consistency).
- **Correctness & Completeness**: Tests asserting that the returned projection completely maps the requested filters and does not drop fields to accommodate terminal width constraints.
