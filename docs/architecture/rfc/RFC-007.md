# RFC-007: Active Workspace

**Author:** Antigravity & USER  
**Date:** 2026-07-14  
**Status:** Proposed  
**Reference RFCs:** RFC-004 (Brain Terminal UX Specification), RFC-006 (Interactive Knowledge Exploration Environment)

---

## 1. Executive Summary

Sprint C Phase 2 shipped ephemeral node pinning as a navigation convenience — a flat list that let users jump back to anchor nodes during deep traversal. Usability observations revealed that users naturally use pins differently: they build a small, focused **working set** for the current task, not a permanent bookmark library.

This RFC formalises that emergent behaviour as a first-class product abstraction: the **Active Workspace**.

An Active Workspace is the user's explicit, visible, session-scoped working context for the current task. It is distinct from search history, bookmarks, and graph collections. Its defining property is **visibility**: anything in the workspace that could influence a daemon query or LLM response must always be shown to the user. The assistant must never use hidden context.

This RFC defines the product model, user workflows, information architecture, and architectural fit. It does not propose implementation or database changes. Persistent workspaces are explicitly out of scope.

---

## 2. Motivation: From Navigation to Reasoning

### 2.1 What the Phase 2 Observations Revealed

The simulated usability session ("Investigating Neural Net Optimization Methods") produced five empirically grounded findings:

| Observation | Finding |
|---|---|
| Average pins per task | 3–6 nodes per focused sub-task |
| Pin lifetime | ~5–15 minutes; cleared when the sub-task ends |
| Revisit frequency | 2–4 visits to the same pin within 10 minutes |
| Navigation pattern | Hub-and-spoke: pin an anchor, traverse spokes, return to anchor |
| Natural organisation | Users do not organise small sets (< 5); clutter emerges when node types mix |

### 2.2 The Gap This RFC Addresses

Phase 2 closes the traversal loop. It does not yet close the reasoning loop.

When a user pins `Adam`, `RMSprop`, and `Momentum`, they intend those nodes to inform their next question. Today they have to manually re-type the node names in the prompt. The workspace and the conversation are two separate mental contexts with no bridge between them.

This RFC defines the product abstraction that enables that bridge — without making context injection automatic or invisible.

## 3. Product Model

### 3.1 What Is an Active Workspace?

> An **Active Workspace** is the user's explicit, named working set of knowledge graph nodes that are relevant to the current task.

Key properties:
- **Explicit**: The user chooses every node in it. Nothing enters the workspace automatically.
- **Visible**: The workspace contents are always rendered in the UI. The user never has to wonder what is in it.
- **Session-scoped**: The workspace exists for the duration of the current TUI session. It is not persisted across restarts (in this phase).
- **Task-aligned**: It represents the current mental task, not a long-term collection. When the task ends, the user clears it.
- **Conversation-independent**: The workspace is not tied to a specific conversation thread. Switching conversations does not destroy it.

### 3.2 How It Differs From Related Concepts

| Concept | Owner | Lifetime | Purpose |
|---|---|---|---|
| **Active Workspace** | User (explicit action) | Session | Working context for the current task |
| **Search History** | System (automatic) | Session | Recall what was queried |
| **Bookmarks** | User (explicit) | Persistent | Long-term saved references |
| **Collections** | User (explicit) | Persistent | Organised topic libraries |
| **Graph Nodes** | Daemon (authoritative) | Persistent | The underlying knowledge base |
| **Conversations** | System | Persistent | Archived dialogue history |
| **Inspector** | System (ephemeral) | Active exploration only | Detailed view of a single node |
| **Breadcrumbs** | System (ephemeral) | Active Inspector session only | Navigation trail within an exploration session |

The crucial distinction between the Active Workspace and bookmarks or collections is **intent and lifetime**. Bookmarks and collections are permanent; the workspace is a whiteboard. Users will clear it as naturally as they clear a whiteboard between meetings.

### 3.3 Workspace Lifecycle

```
[Created implicitly when first node is pinned]
          |
          v
    ACTIVE (contains 1-N nodes)
          |
    +-----+--------------------------------------------------+
    |  User adds nodes (pin from Inspector)                  |
    |  User removes nodes (unpin from Overlay)               |
    |  User opens/closes Overlay                             |
    |  User switches conversations (workspace kept)          |
    +-----+--------------------------------------------------+
          |
          v
    [User explicitly clears] --> EMPTY
          |
          v
    [TUI session ends / process exits] --> DESTROYED
```

Two explicit destruction triggers exist:
1. **User-initiated clear**: `Ctrl+P` → `c` (clear all) or per-node unpin.
2. **Process termination**: On TUI exit, the workspace is not written to disk.

Switching conversations does **not** destroy the workspace. This matches the observed pattern: users pin nodes from one conversation's results and then ask a follow-up in a new conversation, expecting the workspace to persist.

## 4. User Workflows

### 4.1 Primary Workflow: Build Then Ask

```
Conversation Mode
  |  Ask: "Explain Adam optimizer"
  v
Stream Response
  |  Response includes entity references: [Adam], [RMSprop]
  v
Exploration Mode (enter via [Adam] reference)
  |  Inspector shows: relationships, provenance, retrieval explanation
  |  User presses Space -> pins Adam to workspace
  |  Header updates: Workspace (1)
  |  User traverses: Adam -> RMSprop -> Momentum
  |  Pins RMSprop and Momentum
  |  Header: Workspace (3)
  v
Return to Conversation Mode (Esc)
  |  Workspace persists with 3 nodes
  v
Ask: "How do these relate to learning rate scheduling?"
  |  Workspace is visible in the UI
  |  User explicitly attaches workspace to query (Design C -- see section 6)
  v
Daemon receives query + workspace node IDs
  v
Response references Adam, RMSprop, Momentum by name
```

### 4.2 Workflow: Remove a Node

```
Workspace Overlay open (Ctrl+P)
  |  User navigates to RMSprop
  |  Presses Space (or Delete) to unpin
  |  Workspace shrinks: Workspace (2)
  |  Confirmation message: "Unpinned: RMSprop"
```

### 4.3 Workflow: Clear the Workspace

```
Workspace Overlay open
  |  User presses c
  |  Workspace emptied
  |  Header: Workspace indicator disappears
  |  Confirmation message: "Workspace cleared"
```

### 4.4 Workflow: Inspect a Pinned Node

```
Workspace Overlay open
  |  User selects Adam, presses Enter
  |  Overlay closes
  |  Exploration Mode activates
  |  Inspector loads Adam (fresh session, breadcrumbs reset)
  |  User continues traversal
```

This directly implements the hub-and-spoke pattern observed in Phase 2: the workspace is the hub; each Enter starts a fresh spoke from it.

### 4.5 Workflow: Switch Conversations With an Active Workspace

```
Conversation A active, workspace has [Adam, RMSprop]
  |  User presses Ctrl+N (new conversation)
  |  Conversation B becomes active
  |  Workspace state: still [Adam, RMSprop] -- unchanged
  |  Header: Workspace (2) -- still visible
  |  User continues building context in Conversation B
```

The workspace is explicitly **not** conversation-scoped. It is task-scoped, and tasks often span multiple conversations.

## 5. Context Visibility Invariant

> **The assistant must never use hidden context.**

This is a non-negotiable product invariant. Any information sent to the daemon or LLM from the workspace must always be visible to the user before submission. Specifically:

1. The workspace contents are always visible in the header indicator (`Workspace (N)`).
2. The full workspace can always be reviewed before submitting a query (via `Ctrl+P`).
3. Context injection, when implemented, must be explicitly user-triggered — not automatic on every query.
4. The prompt submission UI must clearly indicate when workspace context will be attached (e.g. a status indicator: `[With workspace context]`).
5. The daemon must echo back which node IDs it received as context in any response that uses them, so the user can verify what the LLM actually saw.

This invariant is what separates the Active Workspace from an opaque RAG pre-filter. The user is always the authority over what context is active.

## 6. Context Injection: Design Evaluation

Three designs are evaluated. This RFC does not mandate which is implemented — that decision belongs to the implementation RFC that follows. The evaluation is provided to inform that decision.

### Design A: Never Inject Automatically

**Behaviour**: The workspace is purely a TUI navigation aid. Nothing in the workspace is ever sent to the daemon.

**Advantages**:
- Simplest to implement and understand.
- Zero risk of the assistant using unexpected context.
- No protocol changes required.

**Disadvantages**:
- Breaks the "Build then Ask" workflow (section 4.1). The user must manually re-type node references.
- The workspace becomes a navigation convenience only. It does not close the reasoning loop.
- Contradicts the primary design goal of this RFC.

**Verdict**: Acceptable as a transitional state (current Phase 2). Not acceptable as a permanent design.

---

### Design B: Always Inject the Current Workspace

**Behaviour**: Every query submitted to the daemon automatically includes all pinned node IDs as context, unconditionally.

**Advantages**:
- Simplest user model: "the workspace is always active."
- No extra affordance needed to attach context.

**Disadvantages**:
- **Violates the Context Visibility Invariant (section 5)**. The user may not realise context is being injected, especially when a workspace is left over from a previous task.
- A stale workspace (left over from "optimizer research") will silently contaminate an unrelated query (e.g. "summarise my meeting notes"), producing confusing responses.
- Encourages workspace sprawl: if context is automatic, users lose the incentive to curate and clear the workspace.

**Verdict**: Rejected. Violates the core visibility invariant.

---

### Design C: Configurable Active Workspace (Recommended)

**Behaviour**: The workspace is context-injected only when the user explicitly opts in per query.

The prompt editor gains an attachment toggle, activated by a keyboard shortcut (e.g. `Ctrl+W`):

```
+-------------------------------------------------------------+
| > How do these relate to learning rate scheduling?          |
|                                      [With Workspace]       |
+-------------------------------------------------------------+
```

When `[With Workspace]` is active, the submission includes workspace node IDs. When inactive, the query is clean.

**Advantages**:
- **Satisfies the Context Visibility Invariant**: The user sees exactly when context is attached and can toggle it before submitting.
- Prevents stale workspace contamination.
- Keeps the mental model clean: the workspace is a tool the user picks up deliberately.
- Naturally extends to future designs (workspace profiles, partial attachment, selective node inclusion).

**Disadvantages**:
- Adds one interaction step (opt-in toggle) compared to Design B.
- Requires a new affordance in the prompt editor UI.
- Requires protocol extension to pass workspace node IDs alongside the query.

**Verdict**: Recommended. Balances ergonomics against the visibility invariant. The extra step is the correct trade-off: it keeps the user as the authority.

**On the protocol extension**: The workspace node IDs are passed as an optional field in the existing query message. The daemon treats them as retrieval hints — it does not need to know the workspace model; it only sees a list of node IDs to prioritise. This keeps the daemon ignorant of TUI state.

## 7. Information Architecture

### 7.1 Entity Definitions

| Entity | Definition |
|---|---|
| **Active Workspace** | The user's current working set. A flat ordered list of pinned `PinnedNode` entries. Lives in `UiState`. |
| **PinnedNode** | A single entry in the workspace. Contains: `node_id`, `label`, `node_type`, `pinned_at` timestamp. |
| **Conversation** | A dialogue thread with the daemon. Independent of the workspace. Multiple conversations can share the same workspace. |
| **Inspector** | A read-only detail view of a single node, populated by a full `InspectorModel` from the daemon. Opened during Exploration Mode. |
| **InspectorSession** | The transient state of an active Inspector: loaded model, breadcrumb stack, scroll offset. Destroyed on Esc. |
| **Breadcrumbs** | A navigation history stack belonging exclusively to the active `InspectorSession`. Cleared when the Inspector closes. |

### 7.2 State Ownership

| State | Owner | Lifetime | Notes |
|---|---|---|---|
| `workspace: Vec<PinnedNode>` | `UiState` | Session | Survives conversation switches; destroyed on process exit |
| `overlay: Option<WorkspaceOverlay>` | `UiState` | While overlay is open | Tracks selected index in overlay list |
| `workspace_attached: bool` | `UiState` | Per-query | Resets after each submission (Design C) |
| `inspector_session: Option<InspectorSession>` | `UiState` | Exploration Mode only | Destroyed on Esc |
| `breadcrumbs: Vec<NodeId>` | `InspectorSession` | Active Inspector only | Cleared when Inspector closes |
| `active_messages` | `UiState` | Session | Unchanged — frozen contract from RFC-006 |

### 7.3 State Ephemerality Classification

| State | Ephemeral | Session-Scoped | Persistent |
|---|---|---|---|
| Breadcrumbs | yes (Inspector-lifetime) | | |
| Inspector overlay | yes (Overlay-lifetime) | | |
| Active Workspace | | yes | |
| Workspace attachment flag | yes (per-submit) | | |
| Conversations | | | yes |
| Graph nodes (daemon) | | | yes |
| Pinned nodes (this phase) | | yes | |
| Pinned nodes (future) | | | yes (roadmap) |

### 7.4 Entity Relationship

```
+----------------------------------------------------------------+
|                           UiState                              |
|                                                                |
|  +--------------+   +----------------+   +-----------------+  |
|  |  Workspace   |   | Conversations  |   | InspectorSession|  |
|  |              |   |                |   |                 |  |
|  | [PinnedNode] |   | active_messages|   | InspectorModel  |  |
|  |  node_id     |   | session_list   |   | breadcrumbs[]   |  |
|  |  label       |   | active_session |   | scroll_offset   |  |
|  |  node_type   |   |                |   |                 |  |
|  |  pinned_at   |   +----------------+   +-----------------+  |
|  +--------------+           |                     |           |
|         |                  v                     v           |
|         |          daemon / UdsClient       graph nodes      |
|         |                                  (authoritative)   |
|         +------------------------------------------------------+
|              (optional context injection, user-triggered)      |
+----------------------------------------------------------------+
```

## 8. Architectural Fit

This section explains how the Active Workspace integrates with the frozen component contracts from RFC-006 and `STABLE_UI_INVARIANTS.md`.

### 8.1 Component Ownership Table

| Component | Active Workspace Responsibility | Allowed | Disallowed |
|---|---|---|---|
| **UiState** | Owns `workspace: Vec<PinnedNode>`. Owns `overlay` state. Processes `Action::PinNode`, `Action::UnpinNode`, `Action::ClearWorkspace`, `Action::ToggleWorkspaceAttach`. Computes `workspace_attached` flag. | Mutate workspace list; set overlay index; set attachment flag | Network calls; rendering |
| **Renderer** | Projects workspace contents to header indicator and overlay list. Projects attachment indicator in prompt editor when active. | Read `&UiState` immutably; render cells | Mutate any field; trigger pinning |
| **UdsClient** | When `workspace_attached = true`, includes `workspace_node_ids: Vec<NodeId>` as an optional field in the existing query message. | Serialize the optional field | Cache workspace state; hold workspace between calls |
| **Daemon** | Receives optional `workspace_node_ids` in query message. Uses them as retrieval hint. Returns which IDs it used as `context_used: Vec<NodeId>` in the response. | Use IDs as retrieval hint; echo used IDs | Store TUI workspace state; infer workspace from prior calls |
| **InspectorModel** | No changes required. The Inspector continues to display a single node's full model. The workspace is orthogonal. | — | Merge workspace state into InspectorModel |

### 8.2 Frozen Contract Compliance

- **`state.rs` TUI architecture (Frozen)**: The workspace is a new field on `UiState`. This is an additive change. The typewriter queue, auto-follow, and viewport scroll contracts are untouched.
- **`UdsClient` as pure transport (Frozen)**: Adding an optional field to the query message is a backward-compatible extension. The client continues to make no decisions — it only serialises what `UiState` tells it to.
- **`AppRenderer` as stateless projector (Frozen)**: The renderer reads `workspace` as it reads any other field. It does not mutate it.
- **`InspectorModel` (Frozen)**: No changes. The workspace is orthogonal.
- **Breadcrumb lifecycle (Frozen)**: Unchanged. Breadcrumbs belong to the InspectorSession and are destroyed on Esc.

### 8.3 Protocol Extension Sketch

The query message gains one optional field:

```rust
pub struct QueryRequest {
    /// The user's prompt text
    pub prompt: String,
    /// Session routing
    pub session_id: SessionId,
    /// Optional: workspace node IDs to use as retrieval hints.
    /// Present only when the user explicitly attaches the workspace.
    pub workspace_context: Option<Vec<NodeId>>,
}

pub struct QueryResponse {
    // ... existing fields ...
    /// Echo of which workspace node IDs the daemon actually used.
    /// Empty if workspace_context was None or no nodes were relevant.
    pub context_used: Vec<NodeId>,
}
```

These additions are backward-compatible. Old daemons receiving `workspace_context: None` behave identically to today. Old clients receiving `context_used: []` ignore the field.

## 9. Future Compatibility

### 9.1 Collections (Future)

When collections land, a collection is simply a **named, persistent workspace**. The Active Workspace becomes the "unsaved" state; saving it creates a Collection entry. The `Vec<PinnedNode>` structure is identical — only the persistence layer changes.

```
Active Workspace (session-scoped, Vec<PinnedNode>)
        |
        |  "Save as Collection"
        v
Collection (persistent, named, Vec<PinnedNode> + label + created_at)
```

No redesign of the workspace abstraction is required.

### 9.2 Saved Workspaces (Future)

A saved workspace is a collection without a group hierarchy — just a named snapshot. This maps directly onto the same structure.

### 9.3 LLM Context Profiles (Future)

A user might want different workspaces for different recurring task types (e.g. "Code Review Context", "Architecture Context"). These map onto named workspaces with a quick-switch UI. The active workspace becomes the "current profile." The protocol extension (`workspace_context`) already handles this — only the TUI management UI changes.

### 9.4 Graph Editing (Future)

Graph editing is a separate capability that does not depend on the workspace abstraction. However, the workspace provides a natural staging area: "edit these nodes" could be a context action on the workspace overlay in a future phase.

### 9.5 Selective Context Inclusion (Future)

Design C proposes whole-workspace attachment. A future refinement could allow per-node selection within the overlay before submission:

```
Workspace Overlay (before query)
  [x] Adam         <- included
  [ ] RMSprop      <- excluded by user
  [x] Momentum     <- included
  [Submit with context]
```

This does not require changing the workspace data model — only the attachment UI.

## 10. Open Questions for Implementation Planning

The following questions must be resolved in the implementation RFC before coding begins.

1. **Keyboard shortcut for workspace attachment toggle**: `Ctrl+W` is proposed. Verify it does not conflict with existing Conversation Mode shortcuts.

2. **Overlay layout evolution**: Phase 2 uses a centred modal overlay. The observations noted that a togglable sidebar panel would reduce visual context loss during typing. Should this layout change be included in this phase or deferred?

3. **`context_used` echo rendering**: When the daemon returns `context_used: [Adam, Momentum]`, where in the UI is this shown? Options: inline in the response header, in the sidebar, or as a transient status message.

4. **Workspace attachment reset semantics**: Does `workspace_attached` reset after every submission, or does it stay toggled until manually disabled? "Reset after every submission" prevents accidental context leakage; "stays toggled" reduces repetitive key presses for a sequence of related queries.

5. **Maximum workspace size and usability feedback**: Phase 2 found that > 8 nodes causes list scroll fatigue. Should a soft warning be shown? At what count?

## 12. Manual Acceptance Scenarios

*(To be verified after implementation, not before.)*

### Scenario 1: Context Visibility

1. Pin nodes `[Adam, RMSprop]`.
2. Open the prompt editor.
3. Press `Ctrl+W` to attach workspace.
4. Verify `[With Workspace]` indicator appears in prompt area.
5. Submit query.
6. Verify response references Adam and/or RMSprop.
7. Verify `context_used` echo is shown.
8. Verify that `workspace_attached` is reset (indicator disappears) after submission.

### Scenario 2: Stale Workspace Isolation

1. Pin nodes `[Adam, RMSprop]` while working on optimizers.
2. Clear workspace (`Ctrl+P` → `c`).
3. Ask a completely unrelated question without attaching workspace.
4. Verify the response does not reference Adam or RMSprop.
5. Confirm daemon received no `workspace_context` field.

### Scenario 3: Conversation Switch Preserves Workspace

1. Pin `[Adam]` in Conversation A.
2. Press `Ctrl+N` to open Conversation B.
3. Verify `Workspace (1)` indicator still shows.
4. Open overlay and confirm Adam is still present.

### Scenario 4: Full Nested Transition

```
Conversation A
  -> Exploration -> Pin Adam -> Esc
  -> Ctrl+N -> Conversation B
  -> Ctrl+W (attach) -> Submit
  -> Verify context_used includes Adam
  -> Ctrl+P -> Unpin Adam -> Submit again
  -> Verify context_used is empty
```

## 13. Non-Goals

The following are explicitly out of scope for this RFC and the implementation that follows it:

- **Persistent workspaces**: The workspace is destroyed on process exit.
- **Database schema changes**: No new tables, columns, or migrations.
- **Graph editing or mutations**: The workspace is read-only in this phase.
- **Collections or named workspace groups**: Future capability (section 9.1).
- **Automatic context injection (Design B)**: Rejected.
- **TUI redesign**: Existing layout panels, mode transitions, and focus contracts are unchanged except for the additive attachment indicator.

---

## 14. Summary

The Active Workspace is the bridge between *exploring* and *reasoning*. It transforms pinned nodes from a navigation shortcut into the user's explicit working context — a whiteboard that travels with them across conversations, persists for the lifetime of their task, and can be deliberately handed to the daemon when they are ready to ask a question that builds on what they have found.

The three invariants that define this abstraction:

1. **Explicit**: Nothing enters the workspace without a user action.
2. **Visible**: The workspace is always shown. Hidden context is prohibited.
3. **Task-scoped**: The workspace lives as long as the task does, not longer.

These invariants are what distinguish the Active Workspace from bookmarks (permanent), collections (organised and named), and RAG pre-filters (automatic and invisible). They are the design constraints that must not be traded away in implementation.
