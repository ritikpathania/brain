# ADR-009: Canonical Knowledge Representation via Brain Knowledge Format (BKF)

## Context

Brain processes and indexes information from multiple ingest sources, including local markdown files, Git repositories, local filesystems, PDF documents, Notion pages, Slack workspaces, and email servers. 

Previously, parsing structures and parser-specific ASTs risked leaking directly into storage models (SQLite tables) and retrieval pipelines (vector search, lexical indexes, graph queries). This coupling made adding new ingestion sources complex and increased the risk of semantic data inconsistencies.

## Decision

We introduce the **Brain Knowledge Format (BKF)** as the single, canonical, immutable intermediate model representing all knowledge inside Brain:

1. **Purity and Placement**:
   - BKF types are implemented inside the existing pure domain crate `brain-domain` (under `crates/brain-domain/src/bkf/`) to prevent duplicate competing domain models.
   - The module contains zero external subsystem dependencies (no database engine references, no async runtime requirements, and no logger configurations).

2. **Immutable by Design**:
   - `BKFDocument` fields are private/crate-private and exposed only via read-only getters.
   - Instantiation is restricted to a streamable `BKFDocumentBuilder`, preventing mutation side-effects during downstream retrieval and indexing.

3. **Universal References**:
   - Relationships (`Relationship`) are generalized to target any BKF element (`BKFTargetRef`) rather than being restricted to semantic entities, enabling rich, multi-layered knowledge graphs. (See also: [relations.md](file:///Users/ritikpathania/Developer/PyCharm/brain/docs/architecture/relations.md) for relation types and validation rules).


4. **Correctness by Construction**:
   - The `BKFDocumentBuilder` executes structural verification checks before freezing (duplicate ID prevention, acyclic section trees, and referential integrity validations), guaranteeing that all constructed documents are correct.

5. **Index-Only Embeddings**:
   - Main document structures store index references to vector embeddings (`EmbeddingRef`) rather than storing heavy vector float arrays inline, keeping serialization fast and preventing storage bloat.

6. **Deterministic Serialization**:
   - Semantically identical BKF documents must serialize to identical byte-level layouts, ensuring reliable hashing, deduplication, caching, and cryptographic verification.

7. **Runtime State Isolation**:
   - The document remains completely frozen; retrieval and execution layers must manage their transient data (e.g. search scores, context weights) separately from BKF objects.

## Consequences

- **Pristine Domain Decoupling**: Parsers and ingestion engines act purely as converters that construct `BKFDocument` objects. Storage and retrieval layers operate exclusively on these normalized BKF objects.
- **Architectural Scalability**: Adding a new ingestion source (e.g. an OCR scanner or database connector) requires writing a normalizer that outputs a BKF builder document, without modifying downstream indexing or persistence logic.
- **Enforced Consistency**: Document capabilities and builders isolate structural parsing issues at the edge of the ingestion pipeline.
