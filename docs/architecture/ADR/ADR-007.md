# ADR-007: Tool Execution Cancellation and Abstraction Philosophy

## Context
With the introduction of the tool execution runtime (PR-009), we need to establish clean architectural boundaries between core traits, synchronization primitives, and orchestration/runner implementations. Additionally, we must document clear expectations regarding cancellation semantics for system and user-defined tools.

## Decision
Establish a strict separation of concerns and behavior guidelines for tool registration and execution:

1. **Contracts vs. Runtime Primitives**:
   - **`brain-core`** remains a pure interface/contract crate. It contains traits (`Tool`, `ToolRunner`, `ToolRegistry`, `CancellationToken`) and immutable data carriers (`ExecutionContext`, `ExecutionResult`, `ToolMetadata`). It has no direct dependency on concrete synchronization/runtime frameworks (such as Tokio).
   - **`brain-tools`** (or other runtime crates) implements concrete primitives (such as the Tokio-backed `CancellationTokenImpl` implementing the `CancellationToken` trait) and orchestration coordinators (such as `ToolExecutor`).

2. **Cooperative and Best-Effort Cancellation**:
   - Tool cancellation is **cooperative and best-effort**.
   - The tool runtime coordinator (`ToolExecutor`) guarantees that the calling thread/future stops waiting when cancellation is requested (or timeout is reached).
   - The runtime does **NOT** guarantee that arbitrary, third-party, or blocking tools executing in background threads will immediately terminate.
   - All tools implementing the `Tool` trait should check the `CancellationToken` (provided via `ExecutionContext::cancellation`) periodically during long-running loops or intensive I/O operations and exit gracefully by returning `Err(BrainError::Cancelled)`.

3. **Indirection via ExecutionResult**:
   - To ensure future extensibility without breaking public traits, `ToolRunner::run` and `Tool::execute` return an `ExecutionResult` containing the `serde_json::Value` payload, rather than returning raw JSON values directly. The fields of `ExecutionResult` are read-only and accessed via getters.

4. **Runner Policy-Free Invariant**:
   - `ToolRunner` implementations (such as `BlockingToolRunner`) must never perform policy decisions. They do not perform permission checks, timeouts, cancellation, or retries. All execution policies are enforced solely by `ToolExecutor`.

5. **ToolRegistry Duplicate Prevention**:
   - Registering a tool under a name that is already in use must fail with a `BrainError::InvalidTransition` rather than silently replacing the existing registration.

## Consequences
- **Tokio Decoupling**: The core tool traits in `brain-core` are free of dependencies on specific async runtime details or synchronization types.
- **Robust Orchestration**: By decoupling the raw execution (`ToolRunner`) from permissions, timeouts, and cancellations (`ToolExecutor`), we establish clear extension points for adding retries, metrics, streaming, and execution tracing.
