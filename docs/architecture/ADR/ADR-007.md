# ADR-007: Streaming API Stability Contract

## Context
With the introduction of the decoupled `StreamingRuntime` (PR-015), multiple user-facing clients (Ratatui TUI, future GUI, and CLI or web-based consumers) will consume real-time execution events. To guarantee that frontends do not break as the execution engine and planners evolve, we must establish a stable API contract.

## Decision
We define a strict API stability contract for the Streaming Subsystem to which all current and future clients must adhere:

### 1. Sequence-Based Event Ordering
* **Invariant**: Event ordering is defined **only** by the monotonic `sequence` number.
* **Client Behavior**: Clients must sort and order events strictly based on `sequence` values. They must never rely on timestamps (`timestamp`) for ordering, as system clock drifts or high-frequency event bursts can lead to out-of-order execution times.

### 2. Append-Only Event Schemas
* **Invariant**: The `StreamEventPayload` and sub-events (e.g., `TokenEvent`, `StageEvent`) are strictly append-only.
* **Evolution Rules**: Existing fields will not be deleted or renamed. New payload variants and optional fields may be introduced to support rich telemetry.

### 3. Forward Compatibility (Subscriber Robustness)
* **Invariant**: Subscribers must tolerate unknown event variants.
* **Client Behavior**: Frontend deserializers (e.g., in TypeScript, Rust, or Python) must handle unknown enum tags gracefully. If an unknown payload is received, the client must log a warning and skip/ignore the event without crashing.

### 4. History Replay Ordering Guarantees
* **Invariant**: Late-joining subscribers are guaranteed to receive a complete history of the execution.
* **Details**: When a subscriber calls `subscribe()`, the runtime immediately replays all events from `sequence` `1` to the current state in order before streaming live events. This guarantees gap-free, deterministic catch-up.

### 5. Uni-directional Cancellation Semantics
* **Invariant**: Cancellation flows strictly one-way: Client $\rightarrow$ `StreamingRuntime` $\rightarrow$ `ExecutionContext`.
* **Idempotency**: Invoking `cancel()` on an inactive, cancelled, or already finished execution is safe and behaves as a silent no-op.

### 6. Timeline and Metrics Snapshot Immutability
* **Invariant**: Telemetry data is read-only.
* **Details**: Timeline entries (`TimelineEntry`) and metrics (`ExecutionMetrics`) returned by the runtime are immutable point-in-time value snapshots. Clients must not attempt to modify these structures.

---

## Consequences
* **Client Autonomy**: Decouples presentation development from execution engine changes.
* **Robustness**: Frontends can safely survive minor backend upgrades without code changes.
* **Testability**: Simplifies mock implementations of streams for UI snapshot testing.
