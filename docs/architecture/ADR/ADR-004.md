# ADR-004: In-Memory Event Bus for Subsystem Communication

## Context
Subsystems inside the previous daemon were tightly coupled. For example, retrieval directly triggered SQLite queries, and background consolidation called extraction synchronously. This made it difficult to swap out modules, test components in isolation, or handle asynchronous notifications (like consolidation completion or edge decay sweep results) across boundaries.

## Decision
Introduce a centralized, in-process, typed Event Bus. Communication is separated into:
1. **Commands (Request-Response):** Synchronous execution paths (e.g. Ingest, Query) where the caller expects a structured result.
2. **Events (Fire-and-Forget):** Asynchronous notifications (e.g. NodeInserted, PluginFailed) wrapped in versioned envelopes.

Subsystems interact exclusively by dispatching commands to service layers or publishing/subscribing to events, utilizing abstract `EventPublisher` and `EventSubscriber` traits.

## Consequences
- **Decoupling:** High modularity; components can be removed, replaced, or tested independently.
- **Traceability:** Unified logging and telemetry are achieved by subscribing directly to target events (e.g. `StorageEvent::NodeInserted`).
- **Safety:** Clear boundary separations prevent circular runtime dependency flows.
